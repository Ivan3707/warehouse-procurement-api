# SPA — Warehouse & Procurement API

Backend-сервис для учета складских движений, расчета текущих остатков, контроля складских рисков и планирования закупок.

Сервис хранит движения товаров по объектам и партиям, рассчитывает остатки на основании истории операций, учитывает сроки годности и FEFO, анализирует потребление и формирует рекомендации по закупкам.

Проект реализован как REST API на FastAPI с PostgreSQL и асинхронным SQLAlchemy.

- работа с партиями;

- дату создания.

## Типы складских операций

Поддерживаются пять типов движений.

### Receipt

Поступление товара на склад.

Увеличивает остаток:

```text
stock += quantity
```

Для поступления создается партия с указанными параметрами.

### Consume

Расход товара.

Уменьшает остаток:

```text
stock -= quantity
```

При расходе используется FEFO.

### Writeoff

Списание товара.

Используется, в частности, для списания просроченных партий:

```text
stock -= quantity
```

Просроченная партия не используется как источник обычного расхода.

### Return

Возврат товара.

Увеличивает остаток:

```text
stock += quantity
```

Возврат выполняется для конкретной партии.

### Correction

Корректировка складского остатка.

Положительная корректировка увеличивает остаток:

```text
stock += quantity
```

Отрицательная корректировка уменьшает остаток:

```text
stock += quantity
```

где `quantity < 0`.

Отрицательная корректировка не может привести к отрицательному остатку.

## Расчет остатка

Остаток не хранится в отдельном изменяемом поле.

Он рассчитывается на основании истории движений.

Используется следующая логика:

```text
receipt    + quantity
return     + quantity
consume    - quantity
writeoff   - quantity
correction + quantity
```

Таким образом, текущий остаток является производным значением и может быть восстановлен из истории операций.

Для отдельной партии расчет выполняется по движениям, связанным с этой партией.

## FEFO

Для товаров со сроком годности при расходовании применяется принцип FEFO:

```text
First Expired — First Out
```

Сначала расходуется партия с ближайшим сроком годности.

Например, если имеются:

```text
MILK-OLD   остаток 70   срок 2026-10-04
MILK-NEW   остаток 80   срок 2026-10-19
```

при расходе 100 единиц система сначала использует:

```text
70 из MILK-OLD
30 из MILK-NEW
```

Просроченные партии исключаются из обычного расходования.

Для просроченного остатка используется отдельная операция `writeoff`.

Для товаров без срока годности партия также может использоваться для расхода.

## Защита данных

Реализованы проверки:

- неизвестный товар → `404`;
- неизвестный объект → `404`;
- неизвестная партия → `404`;
- количество поступления или расхода меньше либо равно нулю → `422`;
- количество возврата меньше либо равно нулю → `422`;
- нулевая корректировка → `422`;
- расход больше доступного остатка → `422`;
- отрицательная корректировка больше доступного остатка → `422`;
- операция с будущей датой → `422`;
- повторное использование документа → `409`;
- партия другого товара или объекта → `422`.

Для движений используется уникальность комбинации:

```text
document_number + batch_id
```

Это позволяет использовать один документ для нескольких партий, но запрещает повторное проведение одного документа для той же партии.

## API

### Создание движения

```http
POST /api/movements
Content-Type: application/json
```

Пример поступления:

```json
{
  "sku": "MILK-001",
  "object": "WH-01",
  "operation_type": "receipt",
  "quantity": 20,
  "operation_date": "2026-09-29T10:00:00Z",
  "batch_number": "MILK-TEST-001",
  "expiry_date": "2026-10-15",
  "unit_price": 85.50,
  "invoice_number": "INV-TEST-001",
  "document_number": "DOC-TEST-001"
}
```

Ответ содержит:

- идентификатор созданного движения;
- новый расчетный остаток.

```json
{
  "movement_id": 10,
  "stock": 170
}
```

### Получение движений

```http
GET /api/movements
```

Поддерживаются фильтры:

```text
sku
object
operation_type
date_from
date_to
```

Также поддерживается пагинация:

```text
limit
offset
```

Пример:

```http
GET /api/movements?sku=MILK-001&object=WH-01&limit=20&offset=0
```

Ответ содержит:

- список движений;
- размер страницы;
- смещение;
- общее количество записей после применения фильтров.

Пример структуры:

```json
{
  "items": [],
  "limit": 20,
  "offset": 0,
  "total": 8
}
```

### Получение остатков

```http
GET /api/stock
```

Возвращает остатки товаров по объектам.

Для позиции рассчитываются:

- текущий остаток;
- среднее дневное потребление за 90 дней;
- количество дней запаса;
- ближайший срок годности.

### Детальная информация по SKU

```http
GET /api/stock/{sku}
```

Возвращает:

- SKU;
- название товара;
- единицу измерения;
- остаток по объектам;
- остаток по партиям;
- срок годности;
- цену партии;
- номер накладной.

### Прогноз закупки

```http
POST /api/forecast
```

Расчет выполняется для конкретного SKU и объекта с заданным горизонтом прогнозирования.

Учитываются:

- текущий остаток;
- историческое потребление;
- горизонт прогноза;
- страховой запас;
- срок поставки;
- ожидаемые поставки;
- упаковка;
- минимальная партия поставщика.

Результат содержит:

- прогнозируемое потребление;
- текущий остаток;
- входящие поставки;
- страховой запас;
- точку заказа;
- рекомендуемое количество закупки;
- ориентировочную стоимость;
- рекомендуемую дату заказа;
- объяснение расчета;
- предупреждения.

### Алерты

```http
GET /api/alerts
```

Сервис формирует предупреждения по следующим сценариям:

- недостаточный запас относительно срока поставки;
- риск дефицита;
- критически низкий остаток;
- приближение срока годности;
- отсутствие движений.

Алерт содержит тип и уровень серьезности, а также расчетные показатели, на основании которых он сформирован.

## Расчеты

### Среднее дневное потребление

Используется история расходных операций за последние 90 дней:

```text
average_daily_consumption =
    consumption_90_days / 90
```

### Дни запаса

Если среднее потребление больше нуля:

```text
stock_days =
    current_stock / average_daily_consumption
```

Если потребления нет, количество дней запаса не определяется.

### Страховой запас

```text
safety_stock =
    average_daily_consumption × safety_stock_days
```

### Точка заказа

```text
reorder_point =
    average_daily_consumption × lead_time_days
    + safety_stock
```

### Прогноз потребления

Для горизонта в днях:

```text
forecast_demand =
    average_daily_consumption × forecast_days
```

Для горизонта в месяцах используется соответствующий расчетный период.

### Рекомендуемая закупка

В общем виде:

```text
recommended_purchase =
    forecast_demand
    + safety_stock
    - current_stock
    - incoming
```

Если результат отрицательный, рекомендуемое количество закупки равно нулю.

После расчета количество округляется вверх с учетом:

- размера упаковки;
- минимальной партии поставщика.

Проект разделен на API, прикладную бизнес-логику и инфраструктурный слой.

```text
app/
├── api/
│   ├── routes/
│   ├── routers/
│   ├── schemas/
│   └── dependencies.py
│
├── services/
│   ├── movement.py
│   ├── stock.py
│   ├── forecast.py

│
└── infrastructure/
    ├── database/
    │   ├── models/
    │   ├── base.py
    │   └── seed.py
    │
    ├── repositories/
    │   └── ...
    │
    └── unit_of_work.py
```

### API Layer

Отвечает за:

- HTTP endpoints;
- query-параметры;
- request schemas;
- response schemas;
- преобразование ошибок бизнес-логики в HTTP-ответы.

API не содержит основную бизнес-логику расчета склада.

### Service Layer

Содержит прикладную логику.

Основные сервисы:

```text
MovementService
StockService
ForecastService
AlertService
```

Именно здесь выполняются:

- FEFO;
- проверки складских операций;
- расчеты остатков;
- прогнозирование;
- расчет точки заказа;
- формирование предупреждений.

### Repository Layer

Репозитории инкапсулируют доступ к PostgreSQL.

Например, `MovementRepository` отвечает за:

- создание движения;
- получение движения;
- расчет остатка;
- расчет остатка партии;
- получение партий с доступным остатком;
- получение потребления;
- фильтрацию движений;
- подсчет общего количества записей.

### Unit of Work

`UnitOfWork` объединяет репозитории в рамках одной транзакции.

Используется следующая схема:

```text
service
   ↓
UnitOfWork
   ↓
repositories
   ↓
PostgreSQL
```

При успешной операции выполняется `commit`.

При исключении выполняется `rollback`.

## Проверенные сценарии

### FEFO

При наличии нескольких партий товар расходуется начиная с партии с ближайшим сроком годности.

```text
Batch A:
stock = 70
expiry = 2026-10-04

Batch B:
stock = 80
expiry = 2026-10-19
```

Расход:

```text
quantity = 100
```

Результат:

```text
Batch A: -70
Batch B: -30
```

### Недостаточный остаток

Если доступный остаток:

```text
50
```

а запрашивается расход:

```text
60
```

операция отклоняется с ошибкой `422`.

### Просроченная партия

Просроченная партия не используется для обычного `consume`.

Она должна быть закрыта отдельным `writeoff`.

### Пагинация

При:

```text
limit = 20
offset = 0
```

возвращаются первые 20 записей.

Поле:

```text
total
```

показывает общее количество записей после применения фильтров, но до пагинации.

## Development Motivation

### Почему интересен проект

Проект интересен сочетанием backend-разработки и прикладной бизнес-логики.

Основная сложность заключается не только в создании CRUD API, но и в корректном моделировании складских операций:

- остаток должен быть воспроизводим из истории;
- расход должен учитывать партии;
- просроченные партии нельзя использовать;
- закупка должна учитывать текущий запас и ожидаемые поставки;
- рекомендации должны учитывать срок поставки, страховой запас, упаковку и минимальную партию поставщика.

### Роль в проекте

Backend-разработка:

- проектирование структуры базы данных;
- реализация REST API;
- реализация бизнес-логики;
- работа с PostgreSQL;
- написание репозиториев;
- реализация Unit of Work;
- тестирование;
- контейнеризация;
- настройка миграций и автоматического запуска.
